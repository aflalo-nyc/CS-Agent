AFLALO CS Agent

An agent that reads the shared customer service inbox, understands each unanswered conversation, and writes a reply in AFLALO's voice using only facts it can prove: live order data from Shopify, live prices and stock, Production's garment measurements, and written policy. Every draft goes to a person who reads it and sends it. It cannot send email, and it cannot mark anything read. This page is the one place for the whole project: what it does, how the brain decides, what it knows, how the numbers are measured, how it runs, and how to hand it over.

Using it day to day

The queue lives in Airtable, not in Gmail

Where Airtable base aflalo-cs-pipeline, table CS Drafts. One row per customer email that needs attention. Sort by Priority, then work from the Status column. Read first Why. One line naming the exact rule that produced the Status. Read it before judging a draft. To send a draft Click Open in Gmail on the row. The draft appears inside the customer's thread in the shared inbox as a normal Gmail draft, and the thread opens in front of you. Read, edit, Send. Clicking twice does not make two drafts. If the link ever fails, the page shows the draft text to copy by hand. To teach it Write in Comments + Feedback. A learn step distills comments into binding lessons for every future draft. The 15 lessons from LW's review on Sep 1 are already in force. To measure it Tick Sent and paste what you actually sent into Final Sent Text if you edited it. The gap between draft and sent is the quality score.

The brain: how one email becomes a draft

Two design decisions carry everything. First, the model observes, deterministic code decides. The classifier only describes the email. Plain rules turn that description into draft-or-escalate, so every escalation traces to one named rule and is testable without a model. Second, one grounding container. Every fact the drafter may use enters one structure, and the verifier checks every number, date, and claim in the draft against it. A draft stating anything it can't prove is withheld.

1
Scam netdeterministic, before any model
Built from a real specimen in this inbox, a "Katy Perry premiere" loan request chased from a Gmail address. Looks for impersonation marks: product-out requests around celebrity events, deadline pressure, a freemail follow-up into a professional thread, lookalikes of our own domain, banking-detail changes. One strong mark or two weak ones flag the email. Flagged: no draft of any kind, labeled Possible phishing with the marks listed and the verification step named. On 239 real messages: 3 flagged, none of them customers.
2
Classifymodel call 1
Returns three things and decides nothing: a category (one of 35 scenarios, each defined by the words in its playbook entry), a risk rating, and nine true/false signals: angry or threatening, demands refund or cancel, legal/press/VIP, non-English, time-sensitive deadline, delivery dispute, asks about a money amount, photos already attached, possible scam. It also extracts any order number and the customer's country exactly as she wrote it, never inferred.
3
Routeplain code, no model
In order: risk rated high → human. Any hard signal (scam, anger, money amount, non-English) → human. Category tier human → human. Category needs an order number and none given → draft that asks for it. Category tier manager → draft, gated. Soft signals (refund or cancel request, deadline, delivery dispute, VIP) → keep the draft but gate it, so the human decides from a draft instead of a blank page. Anger is never softened and never exemptable.
4
Look upShopify, read-only
Order status, fulfillment, tracking, dates, line items, customer order count. Catalog and per-size stock for fit and restock questions. Per-country prices with the currency Shopify itself returns, every $0 discarded as a suppressed duplicate page. A failed or ambiguous lookup always wins: an order Shopify can't find goes to a human, never to the drafter's imagination.
5
Retrieve
The scenario's playbook (approach and template from the CS Guide deck), the policy facts it is allowed to state, garment measurements if the style is one of the eight with specs, the whole thread so far, and the three most similar real past replies from the Sent folder as tone reference.
6
Draftmodel call 2
Answer first, lead with the resolution, one line of warmth, the brand sign-off. A missing fact becomes a ______ blank inside an otherwise finished sentence. "Let me check and get back to you" is banned, because the person reading the draft is the one who would check.
7
Verifytwo layers
Layer 1, deterministic: every order number, tracking number, date, amount, measurement, product attribute, discount code, and weekday promise in the draft must trace back to retrieved data. Layer 2, model call 3: a narrow fact-check of the prose against the same data, catching "your order has shipped" written over a status of unfulfilled. Either failing withholds the draft. A verifier that couldn't run counts as a failure, never a pass. Red-teamed with ten planted fake facts: ten caught.
8
Voice lintdeterministic
The deck's rules as machine checks: the exact sign-off, no form-letter phrases, never tell her to contact the carrier, one exclamation point at most, one closing invitation at most, no trailing comfort sentence, no em dashes, never breaks character.
9
Record
Decision, reason, rule, draft, both verification results, the facts used, all appended to the audit database. Then pushed to Airtable with the Status above.

Partial coverage is handled, not hidden. If the template only answers half the question, the drafter says so and the row is marked Draft unverified rather than pretending. If a scenario has no written policy, it is a human-tier category and the pile of those rows is the roadmap for what to document next. The system builds its own to-do list.

Guardrails

  • Cannot send. No credential the service holds has a send permission. A bug cannot email a customer.
  • Cannot mark read, archive, or move. The inbox is opened in examine mode and fetched with peek, so the server itself refuses to set the read flag. There is no label or move operation in the code.
  • Writes to Gmail only on a click. The loop writes to Airtable. The button files exactly one draft into one thread when a person asks.
  • Every fact is traced. Two-layer verification, red-teamed, with a verifier failure counted as a failure.
  • Money is gated. Prices draft at manager tier with the market disclaimer. Refund and cancellation requests get a gated draft. Angry ones and anything rated high risk go to a person with no draft.
  • Scams get silence. Flagged mail receives no draft at all, and the marks are listed for the human.
  • Old mail is never touched. The service drafts only customer messages received after the moment it first started, so the backlog of answered or dead threads is left alone.
  • Each email once. Dedup is in the database, independent of anything in Gmail, so a half-failed pass can't produce a duplicate on retry.

The two KPIs

Both are measured from the mail itself. No tagging, no macro, no discipline required from whoever is answering. The unit is a conversation, identified by Gmail's own thread id, so it survives subject edits. Both numbers are derived from timestamps on every sync, never stored, so a late reply changes them correctly.

KPIDefinitionRules that keep it honest
First response timeHer first message in the thread to our first reply after it.The clock starts at her message, not at an outbound we sent first. Only the first handoff counts. An unanswered thread is blank, never zero.
Resolution timeHer first message to our last reply, counted only once our reply is the last word.If she writes back, the thread reopens and resolution goes blank again while the clock keeps running from her first message. A closing thank-you from her counts as "Resolved, confirmed"; our reply standing last counts as "Resolved, answered". "Thanks, but it still hasn't arrived" closes nothing.
  • Roll up on CS Threads, not CS Drafts. Drafts has a row per message, so a three-message thread would count three times.
  • Scope to customer mail. The Is CS checkbox excludes recruiting, vendor pitches, invoices, and newsletters. A fast reply to a sales pitch flatters no number.
  • Median leads, p90 sets the target. Response times are long-tailed. p90 answers "how bad does it get".
  • Weekly rows follow the 4-5-4 retail calendar (fiscal year from Dec 28, 2025, labels like AUG-D), plus All time and Right now. Each row also splits first response by whether the customer wrote during business hours, Mon to Fri, 9 to 7 ET.
  • Calendar hours, not business hours. A Friday 6pm email answered Monday 9am reads as 63 hours, which is the customer's real wait.
  • Known distortions. Threads that started before the import window report from mid-thread. A reply sent from someone's personal address is invisible and reads as unanswered.

How it runs on Railway

Every 10 minutesWhat happens
1. ImportReads the last 30 days of Inbox and Sent over IMAP, read-only, up to 300 messages per folder. New messages are added to the database; known ones are skipped.
2. DraftFinds conversations where the customer is waiting (her message is the newest, or our last reply promised to come back and never did). Keeps only messages received after go-live. Runs the brain on up to 20 of them.
3. PushSyncs CS Drafts, CS Threads, and CS KPI Summary. Rows with a draft get their Open in Gmail link.

The Open in Gmail button, exactly

The link carries the email's message id and a signature made with a secret only the service knows, so a copied link can't be edited to target another message. When clicked, the service looks up that email's newest draft in its database, signs into the mailbox with the same app password the import uses, and files the draft into Gmail's Drafts folder with the customer's message id in its reply headers. That is what makes Gmail show it inside her thread. The service then redirects your browser to that thread. A placed draft is remembered, so a second click just reopens the thread. An edited draft is a new draft. If anything fails, the page shows the text to copy.

There is no Google OAuth anywhere in this. The app password reads mail and places drafts, and can do nothing else the code doesn't ask for.

Changing the code

A push to GitHub does not deploy by itself. Railway runs a snapshot of the code from its last build. After any commit and push that should go live, kick a build by hand: Railway → aflalo-cs-agent → agent → Deploy. Watch the log for cs agent on … and agent: every 10 min, then open /health. To make pushes deploy automatically, open the service's Settings → Source and reconnect the GitHub repo with the account that owns the Railway project.

Run the tests before pushing: python -m pytest tests/ -q. They need no API key and no network.
